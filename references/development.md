# 开发工作流

先确认受影响业务能力、已有实现/调用方与工作区差异，复用仓库约定。按业务职责与不变量确定归属，不按一个页面/客户/表就另造业务域，不为了遵守模板强加分层、微服务或框架。

按任务加载 frontend.md、backend.md；它们是跨栈规则。若具体框架有已安装适用 Skill，复用它，不在这里复制教程。复杂约束优先使用适合的设计模式，说明它解决的变化点；不要为使用模式增加无用抽象。

## 结构默认值

项目有更具体可适用规范时遵守项目规范；否则手写源文件默认最多500行，函数/方法/构造器默认最多80行（包括外层闭包）。生成文件、vendor、快照数据不按手写规则处理，不能将超限业务伪装成生成文件。拆分要形成职责明确的单元，不压行或按行数机械切片；迁入新项目发现既有超限时避免扩大，不据此开展全库无关重构。

## 确认后的清理

用户确认多次调整后的最终方案时，检查本任务差异和调用链，列出错误尝试留下的代码/路由/配置/文案/资源并删除已经失效的部分。确认引用与构建入口，运行受影响检查。保留仍支撑旧客户端的兼容路径、数据库迁移、有价值的回归测试、必要审计和其它人改动；不能把“旧”作为删除的唯一理由。

尚未提交的错误版本不能假定 Git 已保存。需要保留的历史决策先生成对应快照，代码清理结果记录证据。未确认时可以移除确定无用的本任务临时产物，但不要提前把仍在比较的有效方案当废弃实现。

## 收口

按 batch-testing.md 合并验证前置流程。依项目要求更新本地运行产物；是否部署/推送仍取决于用户授权。达到 handbook-maintenance.md 更新门槛时维护对应知识条目，不给小改动强行生成整套手册。已有手册缺失时提示范围，不因普通修复擅自把任务变成全项目文档重建。
